# `_9` 至 `_11` 降噪器退化分析

后续已通过匹配历史 ABI 的 GPU 派发、双基线对照和单项消融，定位到独立 current 双流与重复视线重建两项主要历史增量。当前 oct32 包含准备及 resolve 的净收益仍未超出波动，详见 [提交消融与 oct32 净收益](bench_culprit_analysis.md)。下面保留原始抓取分析及其适用边界。

后续针对未知 sigma、预计算射线和端点统计的独立派发与连续链对照见 [sigma / ray 复核](bench_sigma_ray_analysis.md)。该轮排除了若干未获稳定收益的候选，修复了饱和 sigma 的数值误判；尚未证明下述倍数回归已解决。

现有抓取支持用户对退化的判断。两域共 12 个空间滤波 pass 的 CS 启动线程总数相同，GR elapsed 周期却由 `_9` 的 21.811M 增至 `_10` 的 46.841M、`_11` 的 44.615M，分别为 **2.148×、2.046×**。统一降噪架构在 `_9` 的候选版本中已经存在；因此应调查统一架构内部新增的访存、重复计算和状态，而不能把路径特化当作主要解决办法。

这些是抓取报告的周期差异，并非毫秒或游戏帧率倍数。相同启动线程数只排除了启动规模这一变量，不代表每线程执行了相同工作。本报告将历史抓取、源码差异、AMD 离线编译和 NVIDIA 链路计时分别标注，避免互相替代。

更干净的对照是两域**前五级**：17,881,430 → 37,254,533 → 36,488,647 周期，即后两份为 `_9` 的 **2.083× / 2.041×**。它避开旧 composite71 还包含反射最终输出、当前另设 composite72 的职责差异；下面十二级合计保留该范围差异，不当作严格同职责计时。

## 1. 先按新增周期确定优先级

数据来自 [All Rules 原始对齐结果](../temp/bench9/profile/comparison_all_rules.json) 和 [逐 pass 摘要](../temp/bench9/profile/pass_summary.csv)。下表的 M 表示百万 GR elapsed 周期；空间组只包含指定的叶级 pass，不再叠加 composite 父范围。

| 组别 | pass | `_9` | `_10` | `_11` | `_9→10` 新增 | `_9→11` 新增 |
| --- | --- | ---: | ---: | ---: | ---: | ---: |
| 大步长空间核 | 54–56、69–71 | 11.117M | 27.831M | 26.135M | **16.715M** | 15.018M |
| 小步长空间核 | 51–53、66–68 | 10.694M | 19.010M | 18.480M | **8.315M** | 7.786M |
| 方差准备 | 50、65 | 2.637M | 6.709M | 6.743M | **4.073M** | 4.107M |
| 12 个空间 pass 合计 | 51–56、66–71 | 21.811M | 46.841M | 44.615M | 25.030M | 22.804M |

前三行互不重叠，最后一行是前两行之和。按 `_9→10` 这三组新增周期排序，应先处理大核，再处理小核与方差准备；这是 **pass 层面的贡献排序**，不能把它解释成“局部性占 16.715M、重复数学占 8.315M、双估计器占 4.073M”。同一个 pass 内的算术、寄存器存活、缓存和延迟隐藏互相影响，消融收益也不能直接相加。

三份抓取的空间线程总数均为 24,975,360：每个小核 2,088,960，每个大核 2,073,600；方差准备每个 pass 也是 2,088,960。源码候选中的小核仍是 16×16 组，大核仍是 8×8 组。`composite98` 的 PS 启动数均为 2,076,480，GR elapsed 周期为 2,837,380 / 2,834,715 / 2,836,945，相对 `_9` 只变化 −0.094% / −0.015%。它在三份抓取及当前生产中均为 fragment 阶段，生产文件是 `composite98.fsh/.vsh`。这个稳定控制范围支持“退化集中在发生较大改动的降噪链路”，但不能据此推算整帧时长或证明所有场景输入相同。

`_10→11` 的空间周期合计下降约 4.75%，并未消除相对 `_9` 的差距；局部还存在反向变化，例如 51 增加 5.76%。因此不能用空间总和的局部改善否认用户测到的退化，也不能只挑改善的 pass 汇报。

`analysis_9.yaml` 的创建和修改时间均为 **2026-08-17 14:18:46**。首选源码参考是 **50b4e66651630e7f9880b462857c24783721ccd1**（当日 13:48:57）；随后紧邻提交是 **81a3ab70aa48e8fb859f6a9495c34c4bc3acbafa**（14:32:35），可能包含抓取时尚未提交的修改。文件时间不能证明抓取的源码哈希，所以保留两个完整归档进行夹逼。统一降噪器已在 **6ad9a54，8 月 15 日 23:26:46** 引入。

小核的共享内存不能只看“是否为零”。50 的源级 tile 大小为 step 1 / 2 / 4 对应 11,664 / 14,400 / 20,736B；81 已先移除共享 geometry，并把它们降至 7,776 / 3,200 / 4,608B；本轮 cached_rays 合入前的小核为 0B。移除 LDS 同时移除了计算复用，必须联合看算术、寄存器状态和真实延迟。

第二流在全部 8 邻居都参与时，额外逻辑访问可达到每有效像素每 pass 的 9×16B 读加 16B 写，即 160B；1920×1080 对应 331.776MB 逻辑请求。它不是实测 VRAM 字节数：邻居复用、缓存、被拒绝 tap 与编译器消除都会改变实际访问。更不能据“有两套估计器”直接断言耗时翻倍。

旧方差准备也有自己的额外工作：50/81 末尾有一次 3×3 variance blur 和 barrier，**37259c2，8 月 17 日 23:11:24** 已将它删除。当前的持续 49 tap 池化与旧版的历史 gate、末尾 blur 应分别计算，不能把所有历史改动都列为新增成本。

**FP16 累加不是 `_9` 较快的成立解释。** 50/81 的亮度与 chroma 累加器本来就是 FP32 `vec4/vec2`；81 只把共享的两个半精度轴值改成 FP32 `vec2`。更晚的 eb75c9d 才引入原生 FP16 主累加，933ec15 又恢复 FP32；两次都晚于 `_9` 文件时间。按现有两个候选，不能归因为“旧版主累加使用 FP16”。

## 3. 联合解释计数器与编译结果

下面选取代表性计数器，而不是把某个百分比直接当作原因。完整规则及每次出现的原始指标仍保存在 All Rules JSON 中；缺失指标没有补零。

| pass / 指标 | `_9` | `_10` | `_11` |
| --- | ---: | ---: | ---: |
| 54：L1TEX hit rate | 68.52% | 32.42% | 35.43% |
| 54：Active Warps per Cycle All | 56.60% | 32.14% | 28.29% |
| 54：Long Scoreboard L1 stall | 12.49% | 12.38% | 10.52% |
| 51：Active Warps per Cycle All（混合阶段，见下文） | 65.08% | 48.14% | 47.97% |
| 51：SM Pipe ALU | 44.38% | 50.36% | 64.95% |
| 51：L1TEX hit rate | 93.04% | 90.00% | 92.63% |
| 51：Long Scoreboard L1 stall | 8.36% | 7.39% | 5.19% |

复核原始阶段计数后，`_9` 的 51 占用率 65.08% 包含 CS 50.04% 和 PS 15.04%，不能把 65.08% 当成旧计算着色器占用率来归因。54 的旧值 56.60% 则确为 CS。对应原始指标与阶段边界说明见 [本轮诊断记录](../temp/bench_culprit/joint_diagnostics.md)。

大核的局部性、活跃 warp 和新增数学／状态需要一起处理。命中率与活跃 warp 同时下降，与逐像素旋转、新增信号流及更长状态生命周期构成一致的调查方向；仅凭这些百分比还不能分配各机制耗时。尤其是 long scoreboard 的比例没有随周期翻倍，不能据此排除访存，也不能把所有新增周期都称为访存等待。

小核则展示了更直接的反例：`_10→11` 的命中率提高、long scoreboard 比例下降，51 的 elapsed 周期仍增加；同时 ALU 比例明显上升。消除部分访存可以把瓶颈转移到重复数学和依赖链，优化判断必须落到连续链路计时，而不是只看缓存命中率。

[同工具链 RGA 对照](../temp/bench9/static_history/aligned_report.md) 使用完整历史归档和当时的 production 源码，目标均为 **AMD gfx1100**：

| 源码 / pass | VGPR | SGPR | LDS 分配 B | 静态指令数 | FP32 FMA | RCP |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 50b4e66 / 51 | 56 | 46 | 11,776 | 938 | 65 | 4 |
| 81a3ab7 / 51 | 56 | 46 | 8,192 | 907 | 66 | 4 |
| current / 51 | 70 | 61 | 0 | 1,003 | 105 | 13 |
| 50b4e66 / 54 | 56 | 50 | 2,048 | 837 | 71 | 4 |
| 81a3ab7 / 54 | 58 | 50 | 2,048 | 783 | 67 | 4 |
| current / 54 | 69 | 78 | 2,048 | 1,014 | 99 | 21 |

同一 AMD 编译目标下，当前版本的寄存器资源、FP32 FMA 与倒数指令增加，小核 LDS 为零；这支持源码中“复用减少、数学与状态增加”的解释。静态指令数不是循环动态执行次数，AMD VGPR/SGPR 也不是 NVIDIA 实际寄存器数，不能将本表换算成 RTX 4060 的占用率或耗时。此处 current 是 cached_rays 合入前的静态分析快照，不是 `_11` 抓取已被源码哈希绑定的证明。

倒数增长还核对到了具体来源：当前 54 的中心、邻域与虚拟位置重建里，分别出现一组分辨率／投影常数的四条 RCP，共十二条；旧版从 geometry.z 解码射线，无需这三组重建。新度量分母、sigma 归一化及两套已知权重的 donor 归一化另有倒数工作。具体 ISA 地址和源码对应见[静态归因](../temp/bench9/static_history/findings.md)，不能仅用“寄存器更多”代替这一层分析。

本机 NVIDIA 导出的 `NVcp5.0` 是中间表示。其虚拟寄存器声明及 `lmem` 常量表不能直接当作最终 SASS 物理寄存器或 spill；通过另一套汇编 API 重编译后的 native query 也不能替代原 GLSL 的最终分配。此前单独两个化简均改善、合并却变慢的反例，需要保持这一边界，不能凭 RGA 或 IR 变短就宣称已找到 NVIDIA 编译器的具体失效原因。

合入的 cached_rays 也有必须披露的 AMD 编译差异，见 [独立审查](../temp/bench9/static_history/cached_rays_review.md)。gfx1100 的 51 自动将八个 tap 完全展开，ISA 从 5,048B 增至 11,496B，VGPR 从 70 增至 72；这表示指令展开，不是动态采样数增至八倍。52/53 则保留循环，VGPR 从 68 降至 62，FP32 FMA 从 111 降至 65，RSQ 从 10 降至 5。54 的 ISA 完全相同。三个小核源级射线缓存为 3,888 / 4,800 / 6,912B，对应 RGA 分配 4,096 / 5,120 / 7,168B，未报告 scratch 或寄存器 spill。NVIDIA 的实测收益不能证明 AMD 同样更快，51 的代码体积与资源增幅仍是实际的跨架构限制。

## 4. 当前消融：保留统一架构，区分可采用优化与诊断

首轮结果见 [screen.json](../temp/bench9/screen.json)。环境为 RTX 4060 Laptop、NVIDIA 610.62、1920×1080。基线是 `temp/bench9/current_shaders`，**不是 `_9` 历史版**。每项测试 diffuse 的连续前五级，31 对 AB/BA；试次前在 query 外用 GPU copy 恢复输入，每条链一个 query，结果查询和数值读回延后，pass 间沿用 0x2028 barrier。coherent 包含连续几何与边界，mixed 用于混合压力覆盖，均使用旋转相机与相互独立的两流输入。

下表百分比为 `100 × (1 − 1 / median(每对基线时间 / 候选时间))`，正值表示链路耗时降低，不是两个独立中位数相除。不同候选收益不可相加。

| 候选 | coherent 耗时降低 | mixed 耗时降低 | 本次输出比较 | 判断 |
| --- | ---: | ---: | --- | --- |
| cached_rays：小核共享同一像素的重建射线 | **7.49%** | **9.11%** | 两流逐位相同 | 数学及采样顺序不变；已完成下述验证并合入。 |
| inactive_virtual：scale 为零时跳过 virtual normal | 3.08% | −1.39% | 两流逐位相同 | 场景相关，尚无稳定单项收益。 |
| cached_rays + inactive_virtual | 6.78% | 10.48% | 两流逐位相同 | 组合收益不等于单项相加；本轮只合入 cached_rays。 |
| diagnostic_group_rotation：恢复组内共用旋转 | **13.37%** | **14.11%** | 两流改变 | 只用于证明采样布局值得调查；改变采样结果，未采用。 |

随后完成了分段与访问消融，见 [causal_controls.json](../temp/bench9/causal_controls.json)。诊断均保持当前统一实现，以降低混入历史 ABI、数学与资源布局差异的风险。

| 消融范围 | coherent 耗时降低 | mixed 耗时降低 | 可得到的结论 |
| --- | ---: | ---: | --- |
| cached_rays，仅连续前三个小核 | **15.86%** | **16.75%** | 两流逐位相同，直接定位了射线重复重建的可消除成本。 |

current passthrough 仍保留 current tap 访问及相关有效性工作，删除累加不等于删除独立流；center_only 又同时改变了 tap 读取和估计器。两个实验说明需要连同访问和依赖一起考察，但不能把 7.76% 与 0.12% 相减当作纯访存成本，也不能将历史双估计器架构直接归因于 2× 耗时。组内旋转的诊断也不能作为等价性能优化合入。

### 已合入实现与最终验证

本轮合入只修改统一 `atrous_small.glsl` 与 `geometry.glsl`：为重叠邻域共享三分量 FP32 primary ray，继续调用原重建表达式，不增加 FP16 或八面体量化。256 个 invocation 协作覆盖 halo，所有线程在任何越界／有效性返回前执行统一 barrier；step 1 / 2 / 4 的 halo 分别为 18 / 20 / 24 平方，覆盖中心、四邻居 virtual normal 及空间 tap。大核仍调用原重建路径。两域继续使用同一算法，tap 顺序、权重、双估计器与输出协议不变。

[完整链数值审计](../temp/bench9/cached_rays_validation.json) 在 17×9、127×73、1920×1080 各执行 37 项检查，默认 debug=0、半精度 ULP 容差为零，**111 项全部通过：108 项输出逐位相同，3 项确认默认视图没有诊断写入**。默认、关闭 EON、关闭五项功能三种配置分别编译 82 个入口，**246 次全部通过**；记录为 [默认配置](../temp/pipeline_audit/bench9_final/report.json)、[EON 关闭](../temp/pipeline_audit/bench9_eon_off/report.json)、[功能关闭](../temp/pipeline_audit/bench9_features_off/report.json)。独立审查同时核对了 halo 唯一写入者、barrier 可达性及访问边界。

## 5. 证据边界与完成标准

All Rules 导出保留了部分 active 周期超过 elapsed、draw/dispatch 数与着色线程数不一致的记录。不能利用这些记录做简单的每 dispatch 归一化，也不能把共享内存分配 stall 的百分比当作实际 LDS 大小。warp stall 的多个类别可能重叠，累计 warp latency 包含并发等待，不能相加成互斥的耗时预算。

RelativeFrameDuration 是帧占比；没有整帧时间就不能得到 pass 毫秒。98 的稳定周期与空间启动量一致提供了有用控制，但没有替代场景、相机、配置、驱动时钟及源码哈希。历史中的 57、63、72 等阶段含义也有变化，不能简单按编号将当前 pass 分类套回 `_9`；81 与 98 的 fragment 身份则保持不变。

当前已确认的是退化的范围、优先级、确切历史工作变化，以及已合入共享射线的数值等价和连续链路收益。保留统一实现、独立 current 的统计语义和当前数学约束，再消除被证明冗余的工作，是可采用优化的边界。恢复 `_9` 性能或获得游戏整体加速，仍须以绑定源码和设置的新游戏抓取确认。
